# Linux 系统调用

系统调用是用户态程序请求内核服务的受控入口，例如读写文件、创建进程或建立映射。C 库函数与系统调用并非一一对应：库函数可能只在用户态执行，也可能组合多个系统调用；部分时间查询还可能通过 vDSO 完成而不进入内核。

## 基本流程

1. **用户态发起请求**：程序通常调用 `read`、`write` 等库包装函数。包装代码按当前架构 ABI 准备系统调用号和参数；没有专用包装时，Linux 的 `syscall()` 可按编号发起调用。
2. **进入内核态**：执行专用系统调用指令或同步异常指令，进入受控的内核入口，保存返回位置和必要的寄存器状态。这不是外部设备触发的 IRQ，也不等于 Linux softirq。
3. **校验与分派**：内核执行入口处理，按配置进行跟踪、安全检查等，再验证调用号并分派到处理函数。服务实现检查参数、权限和用户缓冲区；无效或未实现的调用通常返回 `ENOSYS`。
4. **返回用户态**：完成服务后，内核处理必要的返回工作、恢复状态并返回用户态；库包装将结果交给程序。阻塞调用可能在内核中等待并触发调度，系统调用本身不必然切换到另一个线程。

通常程序从调用处继续执行，但不能概括为所有调用都返回“下一条指令”：`_exit` 不返回，成功的 `execve` 替换原程序映像，信号处理也可能改变恢复执行的路径。调用约定见 [Linux syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html)。

## 关键组件与架构 ABI

| 组件 | 作用与限制 |
| --- | --- |
| 系统调用号 | 标识某一架构和 ABI 下的服务；不能跨架构硬编码同一个数字，应使用 `SYS_*` 等符号 |
| 参数与返回寄存器 | 约定调用号、参数和结果的位置，与普通 C 函数调用约定可能不同 |
| 内核入口 | 保存上下文、处理入口工作并建立受控执行环境 |
| 分派表或分派代码 | 根据调用号选择服务；实现随架构和内核版本变化，不保证始终是运行时函数指针数组 |
| 用户访问与权限检查 | 检查请求是否合法，使用适当用户访问接口搬运数据；用户地址不能直接当作可信内核地址 |

| Linux ABI | 入口指令 | 调用号 | 前六个参数 | 结果 |
| --- | --- | --- | --- | --- |
| x86-64 原生 ABI | `syscall` | `eax` | `rdi, rsi, rdx, r10, r8, r9` | `rax` |
| AArch64 | `svc #0` | `w8`（x8 的低 32 位） | `x0`～`x5` | `x0` |
| RISC-V | `ecall` | `a7` | `a0`～`a5` | `a0` |

表中是系统调用边界的寄存器约定，不是可直接嵌入 C 的完整汇编实现；内联汇编还须声明被破坏的寄存器和内存约束。AArch64 的 SVC 立即数不是系统调用号。

以 [Linux 6.6 arm64 syscall.c](https://github.com/torvalds/linux/blob/v6.6/arch/arm64/kernel/syscall.c) 为例，入口从保存的寄存器取调用号，`invoke_syscall()` 检查范围，经 `syscall_table[array_index_nospec(...)]` 找到处理函数，再保存返回值。该路径说明表驱动分派的一个具体实现，不能代替所有架构和版本的入口分析。

## 错误返回与调用示例

Linux 常见 ABI 使用负错误码作为内核错误结果。普通 C 库包装通常把它转换为返回 `-1` 并设置线程局部的 `errno`；成功时不要根据旧的 `errno` 判断失败。pthread 接口等采用其他约定，详见 [错误代码速查](./错误代码速查.md)。

下面是 Linux/glibc、C11 示例，使用 `<unistd.h>` 的常规包装接口；要求标准输出可写。它处理短写、`EINTR` 和零进展，直接以退出状态报告其他错误，避免错误处理再次依赖输出。若标准输出是已关闭读端的管道，默认 `SIGPIPE` 仍可能终止进程。

```c
#include <errno.h>
#include <stddef.h>
#include <unistd.h>

int main(void)
{
    const char message[] = "hello syscall\n";
    size_t offset = 0;
    const size_t length = sizeof message - 1;

    while (offset < length) {
        ssize_t written = write(STDOUT_FILENO, message + offset,
                                length - offset);
        if (written > 0) {
            offset += (size_t)written;
        } else if (written < 0 && errno == EINTR) {
            continue;
        } else {
            return 1;
        }
    }
    return 0;
}
```

不要把库函数名称等同于实际调用号：例如某些平台的 `open` 包装会使用 `openat`。可在有 `strace` 的 Linux 环境通过 `strace -e trace=write ./syscall-demo` 观察上述程序的写请求；跟踪结果与 ABI、库实现和运行环境有关。

## 字符设备路径与异常返回

打开字符设备时，路径解析与 VFS 获得 inode 和设备号，字符设备机制找到注册的设备与 `file_operations`，随后调用对应的 `open/read/ioctl` 等方法。具体内部函数名随版本变化，驱动仍须检查参数和处理用户访问错误，见 [字符设备与 I/O 模型](../Linux驱动/基础理论/字符设备与IO模型.md)。

AArch64 的 SVC 属于同步异常，IRQ 是异步外部事件。异常入口按来源和栈状态进入向量，结合硬件保存的 ELR/SPSR 和软件保存的通用寄存器恢复执行；不能套用 Cortex-M 的自动八寄存器栈帧。`ret` 是子程序返回，`eret` 是异常返回，二者用途不同。IRQ、softirq 与线程化处理见 [中断处理](../Linux驱动/中断机制/中断处理.md)。
