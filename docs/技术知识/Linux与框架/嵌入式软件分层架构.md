# 嵌入式软件分层架构总结


---

## 一句话核心

**职责要单一，依赖要单向，变化要隔离。**

分层的本质：通过明确职责边界和依赖方向，隔离变化传播，降低维护成本。分层不是为了目录好看或显得专业，而是解决嵌入式项目长期维护的问题。

---

## 一、为什么必须分层

嵌入式项目通常同时面对**四类变化**，如果不分层，这些变化会互相扩散、无序蔓延：

| 变化类型 | 典型场景 |
| --- | --- |
| 平台变化 | MCU 更换、HAL 库升级、RTOS 替换、启动文件调整、CubeMX 重新生成 |
| 板级变化 | GPIO 引脚调整、UART/SPI/I2C 资源变更、DMA 通道变化、中断映射调整 |
| 设备变化 | 传感器/Flash/显示屏/通信模组更换、执行器供应商切换 |
| 业务变化 | 命令定义变化、控制策略升级、状态机调整、参数管理逻辑变更 |

不分层的典型症状：改业务动到底层驱动、换设备影响命令处理、板级引脚一改上层跟着改、某个函数没人敢删。最终变成——**代码不是不能跑，而是不能维护**。

分层的目标：让不同类型的问题在各自边界内闭环处理（平台问题在平台层解决，板级问题在板级层解决，以此类推）。

---

## 二、推荐的六层架构

从上到下越接近硬件；`component` 为横向复用层。

| 层 | 名称 | 定位 |
| --- | --- | --- |
| **app** | 应用层 | 收敛业务变化 |
| **service** | 服务层 | 收敛通用能力 |
| **device** | 设备层 | 收敛设备差异 |
| **bsp** | 板级支持层 | 收敛板级资源差异 |
| **platform** | 平台层 | 承接底层平台环境 |
| **component** | 组件层 | 沉淀可复用能力（横向） |

---

## 三、各层职责详解

### 1. app —— 应用层
- **只负责产品业务本身**：任务调度、命令处理、业务流程、控制策略、状态管理、模式切换、联动逻辑。
- 始终回答一个问题：**产品要做什么？**
- 不关心 GPIO 怎么配、UART 用哪个实例、SPI 怎么收发、设备具体怎么驱动。
- 原则：不直接操作 HAL/CubeMX/寄存器，不关心板级细节，不承担底层初始化装配。
- 一句话：**app 负责"做什么"，不负责"底下怎么做"。**

### 2. service —— 服务层
- 给应用层提供**可复用的通用服务能力**：参数管理、通信服务、协议处理、存储、日志、诊断、升级、告警。
- 特点：不是某个具体设备，也不是某个单独业务，而是能被多个业务共用的能力（如 Modbus 协议栈、参数读写、故障日志）。
- 原则：面向多业务复用、提供稳定接口、不承载产品策略、不写具体设备语义。
- 一句话：**service 是"通用能力层"，为业务提供公共支撑。**

### 3. device —— 设备层
- 对**具体外部器件/功能模块**进行统一抽象：传感器、EEPROM/外部 Flash、LCD/OLED、电机/继电器/蜂鸣器、无线模块。
- 核心价值：把底层总线访问和上层设备语义分开。
- 上层应调用 `temp_sensor_read()` / `flash_write_page()` / `motor_set_speed()`，而不是到处写 `HAL_SPI_Transmit()` / `HAL_I2C_Mem_Read()` / `HAL_GPIO_WritePin()`。
- 原则：屏蔽总线细节、提供设备语义化接口、不写业务流程、不掺杂产品逻辑。
- 一句话：**device 负责"把器件变成可理解、可替换的设备接口"。**

### 4. bsp —— 板级支持层
- 封装 **MCU 片上资源和板级资源**：GPIO、UART、SPI、I2C、ADC、PWM、定时器、外部中断、DMA、板级初始化。
- 把平台/板卡相关细节（哪个 UART 接哪个外设、GPIO 电平是否反向、LED 接哪个引脚、SPI 是否复用 DMA）吸收掉，不泄漏到业务代码。
- 原则：屏蔽 HAL/CubeMX 细节、对上提供稳定板级接口、不写设备语义、不写业务逻辑。
- 一句话：**bsp 解决"这块板子怎么用"的问题。**

### 5. platform —— 平台层
- 项目最底层环境：HAL、CMSIS、RTOS、启动文件、芯片厂商库、CubeMX 生成代码。
- 特点：平台官方提供、自动生成、与芯片架构密切相关。
- 原则：尽量少改、不承载业务代码、上层不要直接依赖、变更谨慎。
- 一句话：**platform 是运行的"地基"，但不是业务开发的主战场。**

### 6. component —— 组件层
- **横向复用层**，沉淀与业务、硬件都无关的基础能力：RingBuffer、CRC、PID、状态机框架、软定时器、FIFO、字符串处理、内存池、事件分发器。
- 原则：与业务无关、与硬件无关、可独立测试、不反向依赖 app/service/device/bsp。
- 一句话：**component 是"可沉淀、可复用、可迁移"的基础能力库。**

## 四、7 条核心设计原则

1. **单一职责**：一个模块只做一类事，不混职责（别一边读传感器一边做业务判断再顺手发协议）。
2. **高内聚、低耦合**：内部逻辑紧密相关，对外暴露接口尽量少，改内部不影响上层。
3. **接口清晰**：通过稳定接口交互，而非 `extern` 全局变量到处穿透；头文件声明清晰 API，输入输出、生命周期、错误码明确。
4. **隐藏实现细节**：上层只关心"做什么"（是否读取成功、当前温度多少），不关心是 I2C 还是 SPI、是 DMA 还是轮询。
5. **禁止越层访问**：不能绕过中间层下探（app 不直接调 HAL，service 不直接访问寄存器，device 不越过 bsp 碰 platform）。
6. **可替换**：换 MCU 时 app 基本不改，换传感器时业务尽量不动，换板卡时 device/service 尽量稳定。
7. **面向接口编程**：依赖稳定抽象而非具体实现——上层依赖"能力"，不依赖"某个具体实现细节"。

---

## 五、运行期调用关系

```
app
 ↓
service / device
 ↓
bsp
 ↓
platform
```

- **app** 面向业务
- **service / device** 提供上层能力
- **bsp** 封装板级资源
- **platform** 提供底层运行环境
- **component** 是横向复用层，可被 app / service / device / bsp 使用，不在主调用链的垂直层上。

---

## 六、初始化关系 ≠ 运行期调用关系

这是很多项目容易混淆的点：**运行期调用关系**和**初始化装配关系**不是一回事。初始化应由统一入口编排，而不是让业务层自己拉起底层。

推荐初始化方式：

```
main
 ├── bsp_board_init()
 ├── device_init_all()
 ├── service_init_all()
 ├── app_init()
 └── app_start()
```

关键：**`app_init()` 不应该直接调用 `bsp_board_init()`**。因为 app 是业务层、bsp 是板级层，业务层负责底层初始化就等于边界倒置。正确做法：由 `main`/系统初始化入口统一编排，各层只初始化自身职责范围，上层在"环境已具备"的前提下启动。

## 七、新模块该放哪一层（6 问判断法）

| 判断问题 | 归属层 | 举例 |
| --- | --- | --- |
| 是不是业务流程、策略、状态决策？ | **app** | 工作模式切换、命令执行流程、设备联动、故障状态机 |
| 是不是给多个业务提供公共能力？ | **service** | 参数管理、协议收发、日志、诊断 |
| 是不是在抽象某个具体外部设备？ | **device** | 温湿度传感器封装、外部 Flash 封装、电机控制接口 |
| 是不是在封装 MCU 片上资源？ | **bsp** | UART 驱动适配、GPIO 读写封装、SPI 总线接口、板级初始化 |
| 是不是官方库、HAL、RTOS、启动文件？ | **platform** | STM32 HAL、CMSIS、FreeRTOS、启动代码、CubeMX 生成代码 |
| 是不是与业务和硬件都无关、可复用？ | **component** | 环形缓冲区、CRC、PID、通用状态机框架 |

**判断优先级**：如果一个模块"好像哪层都能放"，按此顺序判断——**先看职责，再看依赖，最后看复用性**。不是看它"长得像谁"，而是看它本质在解决什么问题、依赖哪些层、未来是否需要复用。

---

## 八、核心结论

- 分层不是增加复杂度，而是**防止复杂度失控**。项目小的时候不分层也能跑，但版本迭代、硬件变更、功能增加、多人协作、Bug 修复、模块复用、平台迁移迟早会到来。
- 真正让项目难维护的从来不是"代码量大"，而是**变化没有边界**。
- 分层的意义不在于形式规范，而在于：**把系统中不同类型的变化，控制在各自应该存在的边界内**——这也是软件架构真正的价值所在。

**六层速记**：
> app 负责业务 · service 负责通用服务 · device 负责设备抽象 · bsp 负责板级资源封装 · platform 负责底层平台环境 · component 负责可复用基础组件。
