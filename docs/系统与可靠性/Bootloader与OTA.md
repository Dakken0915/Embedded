# Bootloader 与 OTA 升级

## 分区与升级状态

引导程序负责选择和验证应用映像。A/B 设计保留当前可运行分区，将新映像写入另一分区。升级元数据记录目标版本、长度、映像摘要、下载进度和启动状态，并使用冗余记录或可恢复的提交方式抵御写入中断。

## 下载与校验

下载协议明确分片序号、偏移、长度、超时、重传和重复包处理。分片 CRC 用于发现传输误码，完整映像摘要用于验证整体内容；安全更新还需校验签名和版本策略，CRC 不能证明来源可信。

写入前检查分区容量和擦除边界；完成后按需要回读校验。只在完整验证通过后提交待启动标志，下载失败或掉电后继续保留旧版本。

## 试运行与回滚

新映像首次启动处于待确认状态。关键外设、配置和主要任务通过健康检查后确认版本；试运行多次失败或超时则由引导程序回滚。配置格式迁移必须兼顾回滚后的旧版本读取能力。

## Cortex-M 应用跳转

跳转前验证目标 MSP、复位入口及向量表地址，停止引导阶段的中断源、DMA 和定时器，并按芯片与移植约定处理待处理中断、向量表、特权状态和栈指针。切换 MSP 后不应继续运行依赖旧栈的普通 C 函数尾声；最终跳转由受控的移植代码完成。

`SCB->VTOR` 是否可用取决于内核。应用的链接地址、向量表布局和引导策略必须一致，不能只把 PC 改为任意 Flash 地址。

## 看门狗与错误恢复

看门狗反映系统整体健康状态，不能由单个高优先级任务无条件喂狗。关键任务应报告进度，健康管理任务检查时间窗后喂狗。独立看门狗与窗口看门狗分别提供不同的时钟和时间约束；升级擦除和重启流程必须纳入看门狗时序设计。

## 分片事务与断点恢复

一片报文可包含会话/映像标识、序号、偏移、有效长度、数据和校验。总包数不能替代映像总长度；最后一包可短于标准分片。所有偏移与长度计算要防止溢出，并在写入前验证其落在目标分区内。

```text
为当前映像创建下载会话并验证版本、大小、目标硬件
准备目标槽，记录已确认的持久化边界
请求期望分片，设置该片独立的重试预算
  超时、长度错误或校验失败：消耗预算，有限重试
  重复已提交片：验证一致后重复应答，不重复改变累计状态
  将来的序号：按协议拒绝或进入有限重排缓存
  正确分片：写入、验证，持久化进度后再确认
完整下载后验证整幅映像及签名
原子提交待试运行记录，再重启
```

累计 CRC 不能对重复片再次更新。进度记录要区分“已收到”和“已可靠写入”，恢复后还需验证 Flash 实际内容；写入中途掉电时，重写前是否需要重擦和回退到擦除单元边界由 Flash 限制决定。

## 试运行计数与失败熔断

在启动新版本前可靠记录尝试次数，避免新固件尚未执行到业务代码就复位而漏计。仅使用 RAM 计数无法跨复位保持。达到尝试上限后回滚并隔离失败映像，防止云端反复触发同一坏版本造成升级循环；成功确认后才能更新稳定版本状态。
