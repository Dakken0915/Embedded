# 内核同步与互斥

本文区分 Linux 6.6 的常规内核与 PREEMPT_RT，并将旧 ARM 内核的锁实现标为历史示例。用户态 pthread 同步另见 [线程控制](../Linux应用/线程控制.md)。

## 原子操作与内存顺序

`atomic_t` 的 `atomic_read/set/inc/dec/add/sub` 以及 `atomic_dec_and_test` 等用于规定的整数操作；`test_and_set_bit`、`test_and_clear_bit` 返回旧位值，而普通 `set_bit` 不返回旧值。原子整数操作不自动保护多个字段组成的不变量，也不能当作 MMIO 寄存器操作。

早期单核 ARM 可通过短暂屏蔽本地中断实现某些原子操作；ARM 独占访问通过 load-exclusive/store-exclusive 检测干扰并重试，较新的架构还可能使用其他原子指令。具体实现由架构与配置决定。关闭本地中断不能阻止其他 CPU 访问，`volatile` 也不提供跨 CPU 的原子性与内存顺序。

对象生命周期引用优先使用 `refcount_t` 等专用接口。需要发布数据时必须选择匹配的 release/acquire 或锁协议，不能假设任意 atomic 读写都包含完整屏障。

## 上下文与锁选择

| 共享访问上下文 | 常规非 RT 内核的常见选择 |
| --- | --- |
| 仅可睡眠任务上下文 | `mutex`，多个读者可考虑 `rw_semaphore` |
| 任务与 softirq | 任务侧 `spin_lock_bh`，双方使用同一锁 |
| 任务/softirq 与 hardirq | 被 IRQ 打断的一侧使用 `spin_lock_irqsave`，按完整上下文统一配对 |
| 严格原子或底层中断控制路径 | 按子系统要求使用 `raw_spinlock_t` |
| 等一次异步操作完成 | `completion`，明确复用和对象生命周期 |

`spin_lock_irqsave` 的顺序是先保存并屏蔽本地中断，再获取锁；否则同 CPU IRQ 可能在锁已经持有时抢占并再次取锁，造成死锁。`spin_unlock_irqrestore` 恢复进入前状态。`_irq` 版本解锁会使能本地中断，只适用于明确知道进入时中断状态的路径。

`_bh` 保护本地软中断相关并发，不是关闭所有硬中断。持普通自旋锁时不能调用可能睡眠的操作，如 `copy_to_user`、`msleep` 或常见的 `GFP_KERNEL` 分配。

PREEMPT_RT 下 `spinlock_t` 可转为基于 rt_mutex 的实现，其抢占和 IRQ 语义与非 RT 不同；`raw_spinlock_t` 仍提供严格自旋约束。不能依靠普通 `spin_lock_irqsave` 在 RT 上实现等同 raw IRQ 禁用的假设。见 [内核锁类型规则](https://docs.kernel.org/6.6/locking/locktypes.html)。

## 自旋锁的访问示例

下面为 Linux 6.6 非 RT 的独立片段，可供任务与 IRQ 路径调用。锁只保护计数器，不在锁内做用户复制、分配或日志输出。

```c
#include <linux/spinlock.h>

struct event_counter {
    spinlock_t lock;
    unsigned long count;
};

void event_counter_init(struct event_counter *c)
{
    spin_lock_init(&c->lock);
    c->count = 0;
}

void event_counter_add(struct event_counter *c)
{
    unsigned long flags;
    spin_lock_irqsave(&c->lock, flags);
    ++c->count;
    spin_unlock_irqrestore(&c->lock, flags);
}

unsigned long event_counter_take(struct event_counter *c)
{
    unsigned long flags, value;
    spin_lock_irqsave(&c->lock, flags);
    value = c->count;
    c->count = 0;
    spin_unlock_irqrestore(&c->lock, flags);
    return value;
}
```

`spin_trylock` 成功返回非零，失败返回 0；`spin_is_locked` 只是瞬时观察，不能作为后续无锁访问的授权。计数器类型仍有溢出边界，需要根据最长消费间隔限制输入速率或采用饱和策略。

## 信号量与互斥量

| 接口 | 成功/失败及上下文 |
| --- | --- |
| `sema_init`、`down`、`up` | 初始化计数、申请和释放；可能阻塞的 down 不用于硬中断 |
| `down_interruptible` / `down_killable` | 成功 0，被相应信号打断返回 `-EINTR` |
| `down_trylock` | 成功 **0**，失败 **1**，与 mutex_trylock 不同 |
| `down_timeout` | 成功 0，超时 `-ETIME`，时间单位为 jiffies |
| `mutex_init` / `DEFINE_MUTEX` | 运行时初始化/静态定义 |
| `mutex_lock_interruptible` / `mutex_lock_killable` | 成功 0，失败不拥有锁 |
| `mutex_trylock` | 成功 **1**，失败 **0** |
| `mutex_unlock` | 由拥有该 mutex 的任务释放，不允许递归或跨任务解锁 |

信号量没有 mutex 的任务所有权，可由其他任务或合规 IRQ 路径 `up`，但这不意味着能在中断中调用会睡眠的 `down`，也不意味着任意次数 `up` 都正确。信号量并不自动在持有者退出时恢复计数。

不可中断等待不代表“永远无法唤醒”，而是不因普通信号中断等待，资源可用时仍可唤醒。`mutex` 的 optimistic spinning 依赖配置和竞争条件，不保证每次竞争都先自旋，也不保证严格 FIFO 公平性。`atomic_dec_and_mutex_lock` 将最后一次引用减少与 mutex 获取协作，不能只用分开的 dec 和 lock 模仿其并发语义。

## 锁的数据结构与执行路径

旧 ARM ticket spinlock 可用 `owner` 与 `next` 两个票号解释：获取者原子取得 next 并递增，等待 owner 等于自己的票号；释放者递增 owner。回绕依实现位宽处理，不是无限整数。该结构不能代表所有 SMP Linux；现代内核可能使用 queued spinlock 或架构专有实现。

单核、无抢占且不启用调试的配置可能消去部分普通 spin 操作，但硬中断并发仍存在；不能从“单核”推出可以删除 irqsave，更不能说系统不再存在其他线程。

Linux 信号量的典型结构包括内部 raw 自旋锁、`count` 与等待链表：

```text
down：内部锁 → count>0 则减一；否则登记 waiter、设置任务状态 → 解锁并调度
up：内部锁 → 无 waiter 则增加 count；有 waiter 则直接交付令牌并唤醒 → 解锁
```

等待者被选中并不要求先将 count 加一再让所有线程竞争。超时与信号路径必须撤销等待节点，内部自旋锁保护计数、链表及交付标志的一致性。

旧 mutex 常以 `count=1/0/负值` 表达空闲、持有和存在等待者，fastpath 用原子操作获取，slowpath 加入等待队列并睡眠。Linux 6.6 常规 mutex 以 owner 及标志、等待锁、等待链表和可选 optimistic spin 队列组织；原笔记的 `__mutex_fastpath_lock`、count 编码不应作为 6.6 字段照抄。

```text
mutex_lock：原子获取 owner 成功 → 返回
          失败 → 可选 optimistic spinning → 加入等待链表 → 调度等待 → 取得所有权
mutex_unlock：清除/交接 owner → 必要时选取并唤醒等待者
```

锁对象须存活到最后一个访问者结束。`lockdep`、锁嵌套顺序及“停止生产—同步回调—释放资源”的退出协议共同约束驱动生命周期，锁本身不能修复已经释放的对象。

## 架构等待与下半部补充

自旋锁可用原子操作及架构等待机制实现，历史 ticket lock、排队锁和具体 ARM64 实现不能混为固定算法。等待队列常使用内核链表组织，但信号量、互斥量及实时优先级等待具有各自结构和唤醒规则，不能说全部都用一种队列。

硬 IRQ 和 softirq/tasklet 等原子上下文不能随意睡眠；普通工作队列和线程化 IRQ 的相应线程上下文通常允许合规睡眠。把所有“下半部”都称作可睡眠是不正确的。共享 IRQ 与任务数据时要选择匹配的锁及 irqsave 等保护策略，并避免持自旋锁调用可睡眠接口。
