# V4L2 驱动与 videobuf2

本文采用 Linux 6.6，用户态格式与采集流程见 [V4L2 视频采集](../Linux应用/V4L2视频采集.md)。旧笔记引用的 AirSpy 是 SDR 设备，可用于解释框架，不能把它的 SDR 缓冲类型直接用于普通视频摄像头。

## 设备注册与 ioctl 路径

| 对象 | 关键内容 |
| --- | --- |
| `v4l2_device` | 驱动实例与子设备等的组织对象，不直接等同于 `/dev/videoX` |
| `video_device` | name、v4l2_dev、fops、ioctl_ops、queue、lock、release、device_caps 等 |
| `v4l2_file_operations` | open/release/read/poll/mmap/unlocked_ioctl 等视频节点入口 |
| `v4l2_ioctl_ops` | querycap、格式协商、控制与 vb2 队列 ioctl 的分派表 |
| `vb2_queue` | 缓冲类型、I/O 模式、私有状态、ops、mem_ops、锁及队列状态 |

典型注册顺序为：初始化驱动状态与锁 → 注册 v4l2_device → 初始化 vb2_queue → 设置 video_device → `video_register_device`。每一步失败逆向回收已经完成的部分。`video_device_alloc` 分配的对象与嵌入私有对象的 video_device 使用不同 release 策略，不能统一直接 kfree。

```text
用户 ioctl
 → VFS → V4L2 core 文件操作
 → 驱动 v4l2_file_operations.unlocked_ioctl = video_ioctl2
 → 用户参数复制、通用校验与 video_device.ioctl_ops 分派
 → 驱动格式/控制回调 或 vb2_ioctl_* helper
```

旧实现中的 INFO_FL_STD/INFO_FL_FUNC 是内部 ioctl 表的分派方式；不是所有 ioctl 都可以无检查地“直达硬件”。复杂参数、兼容 ABI、缓冲类型和设备能力由核心及驱动共同验证。

`video_device.lock` 可串行化一般 ioctl，`queue->lock` 可单独保护队列 ioctl。不同锁之间需固定顺序；DQBUF 等待时使用相应 wait_prepare/wait_finish 释放并恢复锁，避免等待期间阻止生产数据。

## 三组 ops 的分工

| ops | 主要职责 |
| --- | --- |
| `vb2_buf_ops` | 框架在 V4L2 用户缓冲描述与通用 vb2_buffer 之间转换，如 verify_planes_array、fill_user_buffer、fill_vb2_buffer、copy_timestamp |
| `vb2_mem_ops` | 内存后端：alloc/put、USERPTR 获取与释放、DMABUF attach/map/unmap、prepare/finish、vaddr/cookie、mmap 等 |
| `vb2_ops` | 驱动硬件侧：queue_setup、buf_init/prepare/finish/cleanup、buf_queue、start_streaming、stop_streaming 及等待锁协作 |

硬件驱动通常使用现成的 `vb2_dma_contig_memops`、`vb2_dma_sg_memops` 或 `vb2_vmalloc_memops`。不是每个摄像头都分配 vmalloc 缓冲；选择取决于设备 DMA 能力与数据搬运方式。`cookie` 用于取得后端特定句柄，例如 DMA 地址相关对象，不能说没有用途。旧 `vb2_mem_ops` 的函数签名不可直接粘贴到 6.6。

## 缓冲对象与执行路径

`vb2_buffer` 包含 queue、index、type、memory、num_planes、planes 及状态等；`vb2_v4l2_buffer` 增加 sequence、field、flags 等视频信息。每个 plane 保存容量、有效载荷、data_offset、内存后端私有对象或映射信息。一个图像颜色平面与一个 API memory plane 不总是一一对应，必须按像素格式定义解释。

```text
REQBUFS → vb2_core_reqbufs → queue_setup → 分配 buffer/planes/内存
QBUF    → 验证 index/plane → buf_prepare → QUEUED
STREAMON / 满足启动条件 → buf_queue → ACTIVE → start_streaming
完成回调 → 设置载荷、序号、时间戳 → vb2_buffer_done(DONE/ERROR)
DQBUF   → 等待 done_list → buf_finish → 返回元数据 → DEQUEUED
```

`queued_list` 与 `done_list` 属于框架内部状态，驱动不应靠直接改核心链表完成数据交接。通常驱动另有自己的待处理缓冲链表，从 buf_queue 接收缓冲，用 `vb2_buffer_done` 归还；每个取得的缓冲只归还一次。

非阻塞 DQBUF 无完成帧时返回 `-EAGAIN`，阻塞等待可被信号打断。QBUF 前后内存 ownership 与缓存同步由框架、内存后端和设备协议共同管理，不能将 DMABUF map 等同于“建立普通 CPU 虚拟地址”。

## 单平面队列校验片段

下面为固定或预协商 `sizeimage` 的 queue_setup / buf_prepare，调用前 sizeimage 已通过格式协商验证非零，且缓冲布局确为一 plane。它是驱动回调片段，不是完整采集驱动。

```c
#include <media/videobuf2-v4l2.h>

struct demo_video {
    unsigned int sizeimage;
};

static int demo_queue_setup(struct vb2_queue *q, unsigned int *count,
        unsigned int *planes, unsigned int sizes[], struct device *alloc_devs[])
{
    struct demo_video *dev = vb2_get_drv_priv(q);
    (void)count;
    (void)alloc_devs;
    if (!dev->sizeimage)
        return -EINVAL;
    if (*planes)
        return *planes == 1 && sizes[0] >= dev->sizeimage ? 0 : -EINVAL;
    *planes = 1;
    sizes[0] = dev->sizeimage;
    return 0;
}

static int demo_buf_prepare(struct vb2_buffer *vb)
{
    struct demo_video *dev = vb2_get_drv_priv(vb->vb2_queue);
    if (vb2_plane_size(vb, 0) < dev->sizeimage)
        return -EINVAL;
    return 0;
}
```

queue_setup 可能在不同操作及部分分配路径再次调用，不能假定永远恰好执行两次。buf_prepare 只检验容量；采集完成时设置**实际** payload，压缩帧不能一律把 sizeimage 当作 bytesused。设备若要求最少入队数量，应按 6.6 的 `min_buffers_needed` 等规则配置并处理启动失败。

```c
/* Linux 6.6；已取出一个 ACTIVE buffer，硬件/DMA 已结束写入。
 * bytes <= plane 容量；时间戳采用队列声明的单调时间来源。 */
struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
vb2_set_plane_payload(vb, 0, bytes);
vbuf->sequence = sequence++;
vbuf->field = V4L2_FIELD_NONE;
vb->timestamp = ktime_get_ns();
vb2_buffer_done(vb, VB2_BUF_STATE_DONE);
```

完成函数适用的上下文、timestamp flags 与帧序号定义应一致；超容量、截断帧或设备错误要标为 ERROR，不交付未初始化区域。

## 停流与热移除

`stop_streaming` 应停止设备 DMA/USB URB、同步完成 IRQ/工作，再把驱动持有的全部缓冲以 ERROR 归还。`start_streaming` 失败也必须按 vb2 契约退回已经交给驱动的缓冲，通常使用 QUEUED 状态，不能遗留 active 缓冲使用户态永久阻塞。

`video_unregister_device` 使节点不再提供新的打开，但旧 fd 和引用可能仍存在；硬件/私有对象释放应等待最后引用。release 回调与 vb2 队列释放策略必须匹配，不可在 remove 中提前释放所有已映射页。

## UVC 控制与数据链

USB 摄像头通常分为 VideoControl 与 VideoStreaming 接口，控制链由 Camera/Input/Output Terminal、Processing Unit、Selector Unit、Extension Unit 等 entity 构成；编码单元能力依 UVC 版本与设备而定。V4L2 控件 ID 由 UVC 驱动映射到 entity、selector 与位域，应用通常不直接拼接 USB 控制包。

XU 自定义控制即使能从描述符发现，仍可能需要协议文档、权限与映射配置；不能宣称新 UVC 驱动会自动理解厂商所有业务字段。格式/流协商与亮度、曝光控制属于不同路径，应分别处理能力、长度、范围和错误。

接口与生命周期见 [video_device](https://docs.kernel.org/6.6/driver-api/media/v4l2-dev.html) 和 [videobuf2](https://docs.kernel.org/6.6/driver-api/media/v4l2-videobuf2.html)。
