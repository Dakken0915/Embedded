# 中断处理与延后执行

## 硬中断、软中断与软件异常

硬中断（hard IRQ）是 CPU 响应外设、定时器或处理器间中断等请求后，经硬件中断入口进入内核的处理机制。例如网卡完成接收、GPIO 电平变化可以产生 IRQ。触发时机通常独立于当前指令流；硬中断可以打断任务或软中断处理。Linux 的 hardirq 上下文指相应入口和硬中断处理程序所处的执行环境，不是一个可独立调度的普通线程。

Linux 软中断（softirq）是内核延后执行工作的一套机制：先将某类工作标记为待处理，再在合适时机调用该类回调。它不需要用户执行一条“软中断指令”，也不是为每次硬中断自动创建一个线程。网络收发、定时器等子系统使用它处理适合批量执行且不阻塞的工作。

“软件中断”在体系结构材料中还可能指执行指令产生的同步异常，例如 ARM 的 SVC（旧称 SWI）或 x86 的 `int` 指令。Linux 系统调用入口可以使用这类异常或专用系统调用指令，但它们与 `NET_RX_SOFTIRQ` 等 softirq 不是同一机制。用户态信号也不等于 Linux softirq。SVC 与异常帧见 [MCU 启动与异常](../../硬件与接口/MCU启动与异常.md)，Linux 系统调用 ABI 见 [Linux 系统调用](../../Linux应用/系统调用.md)。

以下比较以 **Linux 6.6、未启用 PREEMPT_RT 且未强制线程化的常规 IRQ 路径**为基准；NMI 不属于本表中的普通 IRQ。

| 维度 | 硬中断 hardirq | 软中断 softirq |
| --- | --- | --- |
| 触发与登记 | 硬件中断入口，经 IRQ 层分派到 handler | 内核设置本 CPU 某类 softirq 的 pending 位 |
| 执行内容 | 确认来源、必要的设备应答、保存状态、提交延后工作 | 调用相应子系统回调，批量处理待办工作 |
| 执行时机 | CPU 接受未屏蔽的中断后进入 | 可在退出硬中断等安全点执行，也可由 `ksoftirqd/N` 承接 |
| 本地硬 IRQ 状态 | 常规 hard handler 中本地硬 IRQ 关闭，不应自行开中断制造嵌套 | 回调通常在本地硬 IRQ 开启时执行，可以被硬中断打断 |
| 能否阻塞睡眠 | 不能 | 不能因运行在 `ksoftirqd` 中就调用任意阻塞接口 |
| 多 CPU 并发 | 不同 IRQ 的处理可在不同 CPU 并行 | 同一种 softirq 可以同时在多个 CPU 执行 |
| 与当前任务关系 | 借被打断任务或架构中断栈执行，不能依赖被打断进程的用户资源 | 不是某个用户进程的服务线程，也不能依赖特定用户地址空间 |

“上半部/下半部”描述拆分工作的方法。hard handler 通常作为上半部，下半部可选择 softirq、tasklet、普通工作队列或 IRQ 线程；不能把“下半部”全部等同于 softirq，也不能认为下半部都允许睡眠。相关上下文规则见 [Linux 内核执行上下文说明](https://docs.kernel.org/6.6/kernel-hacking/hacking.html#routines-and-conventions)。

## 从硬件中断到驱动回调

外设产生中断，经中断控制器路由和屏蔽后送达 CPU，架构异常入口保存必要上下文，再由通用 IRQ 层分派到已注册的处理程序；返回时恢复执行。中断响应时机受架构、屏蔽状态和优先级影响，不应描述为所有 CPU 都“每条指令结束无条件检查并立即响应”。

```text
外设状态 → 中断控制器 → 架构异常向量
 → IRQ domain / irq_desc / irq_chip
 → irqaction handler / thread_fn
 → 清除或确认设备中断原因 → 返回
```

硬件中断编号、设备树 interrupt specifier 与 Linux IRQ 号不是同一编号空间。IRQ domain 执行映射；`platform_get_irq` 或 `gpiod_to_irq` 返回 Linux IRQ，负值表示错误。

经典 AArch32 向量表中的 IRQ 常在向量基址偏移 `0x18`，表项可能通过 `ldr pc` 分派；向量基址和 CPU 模式依实现配置。AArch64 使用另一套向量布局，Cortex-M 也不同，不能将“IRQ 地址恒为 0x18”推广到所有 ARM。

## softirq 的登记、触发与执行

### 类型表与每 CPU 待处理位图

Linux 6.6 使用固定的 softirq 类型表，`softirq_vec[]` 保存各类处理函数，每个 CPU 分别维护 pending 位图。`open_softirq` 登记某类回调，`raise_softirq` 标记当前 CPU 上的某类工作待处理；`raise_softirq_irqoff` 要求调用时本地硬 IRQ 已关闭。这些是内核子系统基础机制，普通驱动不应占用别的子系统编号，也不能随意添加一个编号当成可动态申请的 IRQ。

关键数据结构与触发操作如下，来自 Linux 6.6 内核内部接口的节选；依赖 `<linux/interrupt.h>` 和相应 per-CPU/IRQ 实现，不是可直接放入驱动模块的完整程序。

```c
struct softirq_action {
    void (*action)(struct softirq_action *);
};

/* __raise_softirq_irqoff 的核心操作；调用者必须已关闭本地硬 IRQ。 */
or_softirq_pending(1UL << nr);
```

pending 位表示“该类型需要处理”，并不记录发生次数。同一位已置位时再次触发会合并；事件数量和数据必须由子系统队列、环形缓冲区或计数器保存，回调再按相应协议消费。

| Linux 6.6 类型 | `/proc/softirqs` 名称 | 用途 |
| --- | --- | --- |
| `HI_SOFTIRQ` | `HI` | 高优先级 tasklet 路径 |
| `TIMER_SOFTIRQ` | `TIMER` | 普通内核定时器处理 |
| `NET_TX_SOFTIRQ` | `NET_TX` | 网络发送相关延后工作 |
| `NET_RX_SOFTIRQ` | `NET_RX` | 网络接收与 NAPI 轮询等工作 |
| `BLOCK_SOFTIRQ` | `BLOCK` | 块层完成等延后处理 |
| `IRQ_POLL_SOFTIRQ` | `IRQ_POLL` | IRQ 轮询框架 |
| `TASKLET_SOFTIRQ` | `TASKLET` | 普通 tasklet 路径 |
| `SCHED_SOFTIRQ` | `SCHED` | 调度器相关延后工作 |
| `HRTIMER_SOFTIRQ` | `HRTIMER` | 高精度定时器的软执行路径，不代表所有 hrtimer 回调都在 softirq |
| `RCU_SOFTIRQ` | `RCU` | RCU 相关处理，受配置与卸载机制影响 |

类型及 tasklet 定义见 [Linux 6.6 interrupt.h](https://github.com/torvalds/linux/blob/v6.6/include/linux/interrupt.h)。名称中的优先级只涉及相应分派顺序，不能据此保证回调在某个固定时限内完成。

### 执行路径与 ksoftirqd

```text
硬件 IRQ
  → hard handler：确认来源、保存必要状态、提交待办工作
      ├─ 标记 softirq pending
      │    → 退出最外层硬中断等安全点检查 pending
      │    → softirq 分派并调用相应回调
      │         └─ 仍有待办且达到执行限制或需要调度
      │              → 唤醒本 CPU 的 ksoftirqd/N 继续处理
      └─ 或唤醒 IRQ 线程 / 排入工作队列
```

并非每个 hard handler 都会触发 softirq；任务上下文中的内核代码也可触发它。`raise_softirq` 只标记并按条件唤醒，不保证返回前已经执行回调。`__do_softirq` 取出待处理类型，调用对应 `softirq_action`，然后检查新到达的 pending；内核对连续执行设置时间、轮次和调度条件，避免长期占用 CPU。达到条件后剩余工作交给 `ksoftirqd/N`，具体预算是版本实现细节，不是驱动可依赖的时限保证。

`ksoftirqd/N` 是服务相应 CPU 的内核线程，不是一条软中断一个线程。它可被调度，但其中运行的 softirq 回调仍需遵守该回调的非阻塞接口约定；不能因为能在 `ps` 中看到线程，就在回调里使用 `mutex_lock`、`msleep` 或可睡眠的 I2C 访问。需要这类操作时，使用 IRQ 线程或普通工作队列。

典型网络接收链路可由网卡 IRQ 调度 NAPI，再在 `NET_RX` 路径批量处理报文；中断合并和轮询预算使 IRQ 次数、softirq 执行次数、报文数量不存在一一对应关系。触发、分派、预算与 `ksoftirqd` 路径见 [Linux 6.6 softirq.c](https://github.com/torvalds/linux/blob/v6.6/kernel/softirq.c)。

## 并发、屏蔽与可睡眠条件

常规内核的 hardirq、softirq 和 tasklet 回调中不能主动阻塞等待；不能调用 `msleep`、可能阻塞的 mutex/信号量申请、`GFP_KERNEL` 分配或可睡眠的总线访问。`GFP_ATOMIC` 也可能失败，不能用它替代预分配和错误处理。`current` 指针的存在不意味着当前处于可睡眠的任务上下文。

同一种 softirq 可在多个 CPU 并行执行，所以回调中的全局数据仍需要锁或其他并发协议。同一个 tasklet 实例保证不同时在多个 CPU 执行，但不同 tasklet 仍可并行；它也不会自动与 hardirq 或任务访问互斥。Linux 6.6 已将 tasklet API 标为弃用，新驱动优先采用 IRQ 线程等合适机制。

| 操作 | 保护范围与限制 |
| --- | --- |
| `local_irq_save` / `local_irq_restore` | 成对保存和恢复本 CPU 的硬 IRQ 状态；不阻止其他 CPU 访问，不是全局锁 |
| `local_bh_disable` / `local_bh_enable` | 延后本地 softirq 处理；硬中断仍可能发生并设置 pending 位，其他 CPU 仍可运行 softirq |
| 任务侧 `spin_lock_bh`，softirq 侧使用同一自旋锁 | 同时协调共享数据的跨 CPU 访问和本地 softirq 打断；仅禁用 BH 不足以保护全局数据 |
| 与 hardirq 共享状态时使用匹配的 `spin_lock_irqsave` 等方案 | 防止持锁代码被本 CPU 的 IRQ 再次取同一锁；双方须遵守一致协议，临界区保持短小 |

恢复 BH 处理时可能执行待处理 softirq，因此不能在持有该回调所需锁时无意重新开放处理。`in_softirq()` 在仅禁用 BH 时也可能为真，不能单凭它断定正在执行回调；需要区分实际服务状态时可查看版本对应的 `in_serving_softirq()`，接口上下文要求仍以调用契约为准。锁的实现与 PREEMPT_RT 差异另见 [同步与互斥](../基础理论/同步与互斥.md)。

PREEMPT_RT 将许多 IRQ 和软中断路径放入可调度、可抢占的线程环境，并改变 `spinlock_t`、BH 与 per-CPU 保护语义。仍有保持硬上下文的路径，不能概括为“RT 中所有中断都可睡眠”，也不应给通用 softirq 回调加入只在 RT 下成立的阻塞操作。本文常规内核的抢占假设不能直接套用于 RT；参见 [PREEMPT_RT 的执行上下文差异](https://docs.kernel.org/core-api/real-time/differences.html)。

## 注册与线程化中断

`request_irq` 注册 hard handler；`request_threaded_irq` 可将较长处理交给 IRQ 线程。hard handler 只确认中断是否属于本设备、处理必要的硬件状态，再返回 `IRQ_HANDLED`、`IRQ_NONE` 或 `IRQ_WAKE_THREAD`。共享 IRQ 必须区分来源，`dev_id` 需唯一并用于释放。

以下为 Linux 6.6 的 GPIO 线程化中断片段，包含获取 IRQ、读取状态和返回值处理。设备拥有 `button-gpios`，触发方式由 GPIO IRQ 需求确定；本例要求控制器支持双边沿。

```c
#include <linux/gpio/consumer.h>
#include <linux/interrupt.h>
#include <linux/platform_device.h>
#include <linux/slab.h>

struct irq_button {
    struct device *dev;
    struct gpio_desc *gpio;
};

static irqreturn_t button_thread(int irq, void *data)
{
    struct irq_button *b = data;
    int value;
    (void)irq;
    value = gpiod_get_value_cansleep(b->gpio);
    if (value < 0) {
        dev_err_ratelimited(b->dev, "GPIO read failed: %d\n", value);
        return IRQ_HANDLED;
    }
    dev_dbg(b->dev, "button=%d\n", value);
    return IRQ_HANDLED;
}

static int irq_button_probe(struct platform_device *pdev)
{
    struct irq_button *b;
    int irq;
    b = devm_kzalloc(&pdev->dev, sizeof(*b), GFP_KERNEL);
    if (!b)
        return -ENOMEM;
    b->dev = &pdev->dev;
    b->gpio = devm_gpiod_get(&pdev->dev, "button", GPIOD_IN);
    if (IS_ERR(b->gpio))
        return PTR_ERR(b->gpio);
    irq = gpiod_to_irq(b->gpio);
    if (irq < 0)
        return irq;
    return devm_request_threaded_irq(&pdev->dev, irq, NULL, button_thread,
        IRQF_ONESHOT | IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING,
        dev_name(&pdev->dev), b);
}
```

NULL 主 handler 的默认行为用于唤醒线程，`IRQF_ONESHOT` 约束线程处理期间的中断屏蔽；共享中断不能只用该模式不判断来源。GPIO 扩展器访问允许在 IRQ 线程中睡眠，但硬中断里不能调用 `_cansleep` 或 `msleep`。

## 延后执行与退出

| 机制 | 上下文和用途 |
| --- | --- |
| hardirq | 原子上下文，短处理，不睡眠 |
| softirq / tasklet | 常规内核回调不能阻塞睡眠；同一 softirq 可跨 CPU 并发，tasklet 已标为弃用 |
| `timer_list` callback | 常规内核通常由 TIMER softirq 执行，不能直接进行可睡眠总线访问；hrtimer 的硬/软执行模式另行区分 |
| IRQ thread | 任务上下文，按子系统规则允许睡眠 |
| 普通 workqueue | 任务上下文，适合总线 I/O 和延迟工作 |

按键消抖可在 IRQ 中重排 delayed work，等稳定后在工作函数读取 GPIO 并上报；不要在 hardirq 忙等几十毫秒。解绑应先禁止设备继续产生请求或重新排队，再释放/同步 IRQ，最后 `cancel_delayed_work_sync` 等待工作完成并释放对象。不要持有回调需要的锁执行同步取消，否则会死锁。

devm IRQ 的释放发生在设备资源回收阶段；如果 remove 主动释放了工作对象或硬件资源，仍要提前停止 IRQ 与异步访问，不能只依赖 devm 收尾。锁与屏蔽策略见 [同步与互斥](../基础理论/同步与互斥.md)。

普通工作队列依赖 worker 线程提供任务上下文；其执行与并发规则见 [Linux 6.6 Workqueue 文档](https://docs.kernel.org/6.6/core-api/workqueue.html)。

## 中断计数与执行跟踪

Linux 系统已挂载 procfs 时，可以只读查看以下信息；容器和受限环境可能隐藏部分条目。

```bash
cat /proc/interrupts
cat /proc/softirqs
ps -e -o pid,comm | rg 'ksoftirqd|irq/'
```

`/proc/interrupts` 提供 IRQ 等项目的每 CPU 计数，`/proc/softirqs` 提供各类 softirq 的每 CPU 执行计数；比较一段时间内的增量比单看累计值更有意义。次数不直接代表耗时，也不能拿 `NET_RX` 次数当作收到的报文数。`ksoftirqd` 长时间占用 CPU 表示相关处理压力，需要结合实际 softirq 类型、设备流量和回调耗时分析，不能只凭线程名认定硬件故障。procfs 信息见 [Linux /proc 文档](https://docs.kernel.org/6.6/filesystems/proc.html)。

已挂载 tracefs 且内核支持相应事件时，可以先查看事件名称；以下只读取可用列表，不修改跟踪配置。

```bash
rg '^irq:(irq_handler_entry|irq_handler_exit|softirq_raise|softirq_entry|softirq_exit)$' /sys/kernel/tracing/available_events
```

`irq_handler_entry/exit` 观察 hard handler 区段；`softirq_raise` 记录标记待处理，`softirq_entry/exit` 观察执行区段。raise 可能合并，不能将每次 raise 与一次 entry 强行配对；handler 区段也不包含全部架构入口和 IRQ 线程工作。事件分析方法见 [Linux 事件跟踪](https://docs.kernel.org/6.6/trace/events.html)。
