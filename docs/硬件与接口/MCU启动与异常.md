# MCU 启动、异常与缓存

## Cortex-M 启动过程

复位后，处理器从启动映射中的向量表读取初始 MSP 和复位处理程序地址。复位处理程序执行芯片所需的早期初始化，运行时将 `.data` 的初值从 Flash 复制到 RAM，将 `.bss` 清零，再完成 C/C++ 运行时初始化并调用 `main()`。系统时钟设置与段初始化的先后以启动文件实现为准。

全局变量通常具有静态存储期，不因其全局可见性就位于动态堆。局部自动对象通常由栈或寄存器实现，静态局部对象也具有静态存储期。

## NVIC 优先级

NVIC 数字较小的优先级值通常代表更高紧急程度。优先级分组决定抢占优先级与子优先级的位数。抢占优先级决定能否打断正在执行的异常；子优先级用于相同抢占优先级的待处理中断排序。RTOS 的任务优先级编号规则是独立概念，不能直接套用 NVIC 的数值方向。

## PendSV、SysTick 与 SVC

SysTick 可提供内核节拍，用于超时和时间片管理。PendSV 是可由软件置为待处理的系统异常，Cortex-M RTOS 通常将其设为最低优先级，用于在较高优先级中断处理完毕后执行上下文切换。切换通常保存当前任务软件上下文、更新任务栈指针、选择下一任务并恢复其上下文。

SVC 是执行 `SVC` 指令产生的同步异常，可用于系统服务或启动首个任务。异常处理程序可根据异常返回信息选择 MSP 或 PSP，并从栈帧取得返回 PC；在相应 Thumb SVC 调用约定下，可从返回 PC 前的指令读取立即数。具体系统调用编号和参数寄存器由软件 ABI 约定。

## ISR 与任务分工

ISR 应确认或清除中断源，保存必要数据并投递事件。协议解析、日志、大块内存分配和可能阻塞的操作应转交任务。RTOS 中使用符合中断优先级要求的中断专用接口；不能在 ISR 中等待普通互斥量。

## HardFault 信息

故障分析需要保存故障时的 PC、LR、xPSR、MSP/PSP，以及可用的 HFSR、CFSR、MMFAR、BFAR。地址寄存器是否有效由状态位判断。常见原因包括无效访问、栈越界、非法跳转和对齐错误。仅看到 HardFault 名称不能直接确定根因。

## DMA 与 Cache

DMA 和 CPU 若不共享一致性缓存视图，CPU 将缓存中的脏数据清理到内存后，DMA 才能读到新内容；DMA 写入后，CPU 读取前需要按平台规则使对应缓存行失效。缓冲区还需满足缓存行对齐和所有权约束，避免失效操作丢弃同一缓存行内的其他脏数据。实际代码使用平台 DMA 接口，不能把 `volatile` 当作缓存维护。

## Cortex-M 寄存器与异常帧

在常见 AAPCS32 约定下，R0～R3 用于部分参数及结果，R4～R11 包含被调用者保存寄存器，R12 为临时寄存器，R13 为 SP，R14 为 LR，R15 为 PC；浮点参数及复合对象还有其他规则。局部对象可能被优化掉、放入寄存器或栈，不能仅按局部变量数量推算切换帧。

Cortex-M 基本异常帧保存 R0～R3、R12、LR、PC、xPSR。软件切换还处理其余必要状态，浮点扩展帧、对齐填充和安全扩展会改变布局。异常入口不会通用地“关闭全部中断”，更高紧急程度异常仍可能嵌套。

## PendSV 的置位与最低优先级

以下代码使用 CMSIS 和支持 PendSV 的 Cortex-M 内核，交由 RTOS 端口管理；不应在应用中随意覆盖内核已设定的优先级。

```c
/* CMSIS 设备头由具体芯片提供。 */
void requestContextSwitch(void)
{
    SCB->ICSR = SCB_ICSR_PENDSVSET_Msk;
    __DSB();
    __ISB();
}
void configurePendSvPriority(void)
{
    NVIC_SetPriority(PendSV_IRQn, (1u << __NVIC_PRIO_BITS) - 1u);
}
```

ICSR 的写一置位语义宜直接写相应位，避免对具有特殊位语义的寄存器随意读改写。NVIC_SetPriority 使用未左移的逻辑优先级；其有效位数由 __NVIC_PRIO_BITS 给出，不应对所有芯片统一填 0xFF。

## SVC 调用号提取

下面为 ARMv7-M Thumb、基本异常帧的 GNU 汇编示意，不包含完整服务分派和安全检查，不能覆盖 RTOS 自带 SVC 入口：

```asm
.syntax unified
.thumb
SVC_Handler:
    tst lr, #4
    ite eq
    mrseq r0, msp
    mrsne r0, psp
    ldr r1, [r0, #24]
    ldrb r1, [r1, #-2]
    b svc_dispatch
```

栈中的 PC 指向 SVC 之后的返回位置，调用号来自前两个字节处的指令立即数字节。扩展浮点帧或其他架构布局需另行处理。非特权入口还须验证指令来源、参数地址和调用权限。

并非所有 FreeRTOS API 都通过 SVC，普通非 MPU 端口常直接调用内核 C 函数；SVC 可用于首次启动或受保护服务，实际角色由端口定义。

## 故障现场保存与恢复边界

故障记录应先保留原始栈帧和状态寄存器，再进行耗时输出。CFSR 的有效位决定 MMFAR/BFAR 是否可用；堆栈错误时不能继续假定原 SP 指向可安全解引用的完整帧。PC 和 LR 可结合 ELF 符号与反汇编定位指令，但非法跳转可能使它们本身不可信。

### HardFault 定位流程

以下以具有相应故障寄存器的 Cortex-M3/M4/M7 为范围；M0/M0+ 和带安全扩展的内核需按对应手册调整，不能读取不存在的寄存器。

1. 在处理程序入口或故障记录中取得异常入口 LR（EXC_RETURN）、原始 MSP/PSP、HFSR 与 CFSR。HFSR 的 FORCED 表示可能有可配置故障升级为 HardFault，应继续检查 CFSR；不要先清除状态位或重启覆盖现场。
2. 根据 EXC_RETURN 判断异常前所用栈、基本/浮点扩展帧，并检查入栈/出栈错误和栈边界，再读取被打断现场的 PC、LR 与 xPSR。处理程序内的当前 PC/LR 不等于任务出错时的 PC/LR，普通 C 函数序言也可能已经改变 MSP。
3. 结合 CFSR 区分访问权限、总线、非法指令、无效状态等故障；MMARVALID/BFARVALID 置位时才解释相应地址。精确访问故障通常可以结合堆栈 PC 查看指令和操作数；非精确总线故障的 PC 可能晚于真正错误指令。
4. 使用同一次构建的 ELF、符号和反汇编定位源码，检查相关指针、返回地址、任务栈高水位和越界写。FreeRTOS 中还需核对 ISR 调用 API 的优先级限制、任务栈与 TCB 是否已被破坏，不能只凭故障名认定栈溢出。

例如，主机安装 Arm GNU 工具链后，可将已确认的故障地址替换到以下命令；`0x08001234` 只是占位地址，不能作为所有固件的固定位置：

```bash
arm-none-eabi-addr2line -e firmware.elf -f -C 0x08001234
arm-none-eabi-objdump -dS firmware.elf
```

源代码优化、内联及损坏的返回链都可能影响定位。故障处理路径避免调用可能拿锁、分配内存或阻塞的 printf/RTOS 服务；通常先写入预留的固定记录区，再选择受控停机或复位。若使用保留 RAM 跨复位读取，还需由链接脚本、启动代码和芯片复位域共同保证不被清零；不应默认从 HardFault 直接返回便能恢复正常。寄存器布局和访问接口见 [CMSIS SCB](https://arm-software.github.io/CMSIS_6/latest/Core/structSCB__Type.html) 与 [内核寄存器访问](https://arm-software.github.io/CMSIS_6/latest/Core/group__Core__Register__gr.html)。

### “无损调试”与低干扰观测

若“无损”指保持原始故障信息，应在修改寄存器、清除故障位或复位之前保存现场；若指不暂停正常运行，则通常是低干扰观测，不能保证零时间开销、零带宽限制且绝不丢数据。

| 方式 | 能力与限制 |
| --- | --- |
| SWD/JTAG 断点、DWT 数据观察点 | 适合检查故障现场或捕获越界写；触发停机会改变任务、中断和外设的时间关系 |
| GPIO 翻转与逻辑分析仪 | 可观测延迟和时序，占用引脚并增加少量指令/总线访问 |
| ITM/SWO、可用的 ETM 跟踪 | 输出事件或指令轨迹，依赖芯片、引脚、探针和带宽；并非全部 Cortex-M 都支持 |
| RTT 或内存环形记录 | 可在运行期间提取数据，仍消耗 CPU、RAM 和总线资源；阻塞模式可能等待，非阻塞模式缓冲满时可能丢弃 |

记录应限制长度与频率，并在多生产者场景处理并发。故障路径需要独立、可用的存储和尽可能少的依赖；没有连接调试器时，不要无条件执行可能再次引发异常的 BKPT。RTT 的缓冲与运行模式见 [SEGGER RTT 文档](https://www.segger.com/products/debug-probes/j-link/technology/about-real-time-transfer/)。

Cortex-M3 与 Cortex-M7 都不能简单按桌面乱序处理器模型解释。M7 常有更复杂流水线、Cache、TCM 和可选浮点支持，M3 的典型存储与执行结构不同；具体性能、异常与 Cache 行为须按芯片实现判断。
